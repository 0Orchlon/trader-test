## 0. Энэ баримтын хамрах хүрээ

Энэ бол **SPEC** шатны гарц: систем ЮУ хийхийг, түүнийг ХЭРХЭН ШАЛГАХЫГ тодорхойлно.
Архитектур (`lld.md`), contract-ын эцсийн хувилбар (`contracts.yaml`), ажлын задаргаа
(`tasks.md`) нь дараагийн шатуудын гарц — энд ОРООГҮЙ. Хавсралт 02–05-д өгөгдсөн
техникийн шийдлүүдийг энд зөвхөн **шаардлагыг шалгах боломжтой болгох хэмжээнд** иш татав.

> **Ойлголтын хязгаарлалт (хавсралт 00-оос авав, дахин батлав):** энэ систем нь
> арилжааны ашгийн хувь хэмжээг баталгаажуулахгүй. «99.9999%» гэдэг нь зөвхөн
> **инженерийн найдвартай байдалд** хамаарна: өгөгдөл зохиохгүй, эрсдэлийн хязгаар
> тойрохгүй, чимээгүй унахгүй, бүгдийг бүртгэнэ. Ашигт ажиллагааны амлалт энэ спекийн
> хамрах хүрээнд БАЙХГҮЙ.

## 3. Хамрах хүрээ (v1)

### 3.1 Дотор

- Alpaca **Trading API**: US equities/ETF ба crypto. Paper (`paper-api.alpaca.markets`)
  ба live (`api.alpaca.markets`) — нэг код, зөвхөн config-оор солигдоно.
- Order төрөл: `market`, `limit`, `stop`, `stop_limit`, `bracket`.
- Нэг backend (REST + WebSocket), Postgres + Redis-тэй.
- Нэг frontend dashboard: positions, orders, equity curve, agent decision feed,
  approval queue, kill switch, provider switcher, auto-tuning panel, settings,
  **гарал үүслийн (origin) харагдац**, **гарын арилжааны ticket**, **системийн
  төлөвийн удирдлага** (зогсоох / унтраах бэлтгэл / идэвхжүүлэх).
- Арилжааны төлөвийн машин: `ACTIVE` → `WINDING_DOWN` → `HALTED`; `HALTED`-аас
  гарах цорын ганц зам нь operator-ийн `activate` үйлдэл.
- Agent Gateway: нэг provider-agnostic Tool Contract; Research role-ийн provider-ыг
  ажиллаж байхад нь солино.
- Whitelist-д байгаа цөөн тоон параметрийн хязгаарлагдмал auto-tuning — анхдагчаар
  зөвхөн backtest/paper.

### 3.2 Гадна (v1-д ХИЙХГҮЙ)

| Гадуур зүйл | Шалтгаан |
|---|---|
| FX арилжаа | Alpaca FX санал болгодоггүй. Дараа хэрэгтэй бол `BrokerPort`-ийн хоёр дахь adapter — backlog, v1 биш. |
| Хүний хяналтгүй бүрэн автомат live арилжаа | Өдрийн алдагдлын kill switch ба position cap нь боловсорсон үед ч ЗААВАЛ үлдэнэ. |
| Market-making, HFT, sub-second стратеги | Alpaca REST/WS latency тохирохгүй. Хамрах хүрээ = swing/intraday. |
| Татварын тайлан / нягтлан бодох бүртгэл | Alpaca өөрөө маягт гаргадаг. Энэ систем зөвхөн өөрийн бүртгэл хөтөлнө. |
| Operator-оос бусад хүнд зөвлөгөө өгөх / бусдын нэрийн өмнөөс арилжаа хийх | Зохицуулалттай үйл ажиллагаа болно. Re-scope шаардана. |

## 6. Хүлээн авах шалгуур (AC)

Шалгуур бүр **шалгаж болохуйц**: ямар үйлдэл хийхэд ямар үр дүн гарахыг, унах нөхцөлийг нь
заана. §7-ийн тоон хязгаарууд нь config утга тул шалгуурууд нь тэдгээрийг *нэрээр* иш татна —
тоо солигдоход шалгуур хүчинтэй хэвээр.

## 7. Эрсдэлийн хатуу хязгаар — **operator тогтооно** (SPEC_APPROVE-ийн гарц)

Доорх тоонууд нь **батлагдаагүй саналууд** (хавсралт 06 §1-ийн жишээ утгууд).
Эдгээр нь код дотор анхдагчаар суух ёсгүй; operator SPEC_APPROVE дээр бодит утгыг
тогтоож гарын үсэг зурна. §6-ийн шалгуурууд тоог нэрээр иш татдаг тул утга солигдоход
шалгуурууд хүчинтэй хэвээр.

| Config нэр | Утга | Санал болгож буй эхлэл (батлагдаагүй) |
|---|---|---|
| `MAX_POSITION_PCT` | Нэг symbol-д ноогдох дээд хувь (equity-ээс) | 10% |
| `MAX_TOTAL_EXPOSURE_PCT` | Нийт байрлалын дээд хувь | 100% (leverage-гүй) |
| `DAILY_LOSS_LIMIT` | Өдрийн алдагдлын kill-switch босго | equity-ийн 2% |
| `MAX_DAY_TRADES` | Equity < $25k үед 5 ажлын өдрийн day trade-ийн дээд тоо | 3 (PDT дүрэм, US/FINRA) |
| `MAX_ORDER_NOTIONAL` | Үүнээс дээш order бүр заавал хүний зөвшөөрөлд очно | $1,000 |
| `RESTRICTED_SYMBOLS` | Арилжаа хориглох symbol-ийн жагсаалт | operator тодорхойлно |
| `ERROR_RATE_LIMIT` | Circuit breaker-ийн API алдааны түвшний босго | тодорхойлоогүй |
| `REJECT_RATE_LIMIT` | Circuit breaker-ийн order татгалзлын түвшний босго | тодорхойлоогүй |
| `APPROVAL_TTL` | Зөвшөөрлийн мөрийн хүчинтэй хугацаа | тодорхойлоогүй |
| `WIND_DOWN_GRACE` | «Унтраах бэлтгэл» товчноос хойш позиц хаах боломжтой хугацаа; дуусахад `HALTED` | тодорхойлоогүй (санал: 15 минут) |

⚠ Эдгээр хязгаарын дараагийн ямар ч өөрчлөлт нь энгийн код өөрчлөлт БИШ — SPEC →
SPEC_APPROVE-ийг дахин дайрна. Хязгаар бол бодлого, хэрэгжүүлэлтийн нарийн ширийн зүйл биш.

## 8. Хууль, ёс зүйн хүрээ (шаардлага болгон)

- **Alpaca-ийн Terms of Service** нь API-аар юу зөвшөөрөгдөхийг тодорхойлно. Энэ спек
  нь Trading API-ийн стандарт жижиглэнгийн хэрэглээг таамаглаж байна.
- **PDT дүрэм** (US/FINRA): equity $25,000-аас доош үед 5 ажлын өдөрт 4+ day trade хийвэл
  хамаарна. Risk Agent нь AI-ийн юу санал болгосноос үл хамааран үүнийг мөрдүүлнэ (AC-4).
- **Зах зээлийн манипуляци хориотой:** spoofing, layering, wash trading үүсгэх загвар
  хэрэгжүүлэхгүй. CODE_REVIEW-ийн байнгын checklist зүйл.
- **Харьяалал:** operator US-аас гадна (Монгол) байрлаж байгаа бол өөрийн улсын татвар,
  зохицуулалтын үүрэг өөрт нь хамаарна. Энэ систем түүнийг хариуцахгүй.
- **Хөрөнгө оруулалтын зөвлөгөө биш:** системийн дотор LLM-ийн гаргасан текст нь
  operator-ийн өөрийн шинжилгээний хэрэгсэл — гуравдагч этгээдэд зөвлөгөө болгон
  түгээхгүй.
- **Provenance нуухгүй:** audit trail-д шийдвэр бүрийн гарал үүсэл (аль agent, аль
  provider/model) бүртгэгдэнэ, хүний шийдвэр мэт харуулахгүй.
- **UI-д dark pattern байхгүй:** gamified streak, түлхэц өгөх мэдэгдлийн спам гэх мэт
  operator-ийн хүслээс илүү арилжаа хийхэд өдөөх зүйл хийхгүй.

## 11. v1-ийн амжилтын шалгуур

1. Live идэвхжүүлэхээс өмнө **30+ дараалсан хоног** paper арилжаа: эрсдэлийн хязгаар
   зөрчсөн = 0, order замын барьцаагүй exception = 0, төлөвийн зөрүү = 0,
   grounding алдаа = 0 (AC-13).
2. Дор хаяж **хоёр өөр LLM provider** ижил Research role-ийг амжилттай ажиллуулж,
   Risk Agent-ийн шийдвэр ижил гарна (AC-11).
3. Дор хаяж **нэг удаа** зөвхөн лог дээрээс арилжааг бүрэн сэргээн харуулна (AC-18).
4. Kill switch ба circuit breaker-ийг UAT дээр санаатай ажиллуулж, шинэ order
   зогссоныг батална (AC-14, AC-15).
5. «Унтраах бэлтгэл → grace дуусах → процесс унтраах → дахин асаах → `activate`»
   бүтэн мөчлөгийг UAT дээр нэг удаа гүйцэтгэж, дахин асаасны дараа систем
   `ACTIVE` болж БОСООГҮЙг батална (AC-36, AC-37).
